# PB Trading Assistant: cloud deployment

This bundle adds a Linux container entry point to the consolidated PB research assistant. It does not deploy anything automatically or enable broker execution. The existing signal qualifications, calendar review requirement, group permissions, manual journal and dashboard are unchanged.

## Hosting requirements

Use a permitted always-on container service or Linux VM, with internet access to Telegram and the market-data provider, enough RAM for pandas/yfinance/exchange-calendars, and a durable private single-writer disk. One replica only. No public HTTP endpoint is required. Check the provider's actual plan, resource limits, permitted use, cost and retention before provisioning. Northflank's free Developer Sandbox is a candidate for testing (not a production SLA); a persistent volume's inclusion in the free allowance has not been confirmed. Do not select paid resources without approval. Do not use ephemeral storage as a journal substitute.

Deploy from this package's Dockerfile. Configure a persistent volume at `/data` (single replica, writable by container UID/GID 10001). The startup checks that the path is an explicit Linux mount point; this does not independently prove a provider's storage durability. Confirm it is truly persistent in the provider console. Configure `PB_TELEGRAM_TOKEN` as a **runtime secret** in the host's secret manager. Never paste it into chat, commit it, bake it into the Docker image, or log it. The entry point is `python -u cloud_start.py`.

## Move the existing local assistant

1. Stop any prior local foreground assistant (Ctrl+C), and if installed as a launch agent run `bash stop.sh` from the original consolidated package. Do not run two polling instances with the same bot token. Do not delete the local journal.
2. If you want to retain the existing journal and pairing, create a private consistent backup on your Mac with `python3 export_journal.py "$HOME/pb-journal-private.sqlite3"`. Run the script from this package after stopping the assistant. It exports only the SQLite journal and checks integrity; it does not export the token. Keep this file private; it contains journal records and Telegram IDs. Transfer it using your host's secure private file transfer to `/data/journal.sqlite3` before starting the service. Set ownership/permissions so UID 10001 can read and write it. Retain the Mac backup. Never upload it to the public GitHub repository or a public artifact. If you intentionally want a fresh journal instead, explicitly set `PB_ALLOW_EMPTY_JOURNAL=1`, pair privately using the code in your private host log and remove the flag once initialized. This will not preserve old journal entries.
3. If you have a legitimately reviewed calendar file, transfer it privately to `/data/calendar_review.json`. Refresh it on the same review schedule as documented in README.md; the cloud service will not invent calendar coverage. Missing/expired coverage blocks qualified signals. Historical cache is optional and may be regenerated.
4. Start the cloud worker; verify logs show the existing bot identity and successful startup. In Telegram privately send `/status`, `/dashboard`, and `/journal`; verify the group with `/groupdemo`. Verify data freshness and news coverage during a real session. Restart the worker and confirm the same journal and group linkage remain. Only after these checks should you consider the Mac independent of the service. A test example is not a real market signal.

The host may reject outbound requests or have insufficient memory; this package does not establish live market data availability or actual uptime. The Docker image and hosted deployment have not been built/tested in this environment. The Python offline regression suite covers the cloud preflight checks and prior strategy/journal behavior. No paid cloud resources or accounts have been created. GitHub connector writes remain denied (403), so no remote source or workflow has been changed.
